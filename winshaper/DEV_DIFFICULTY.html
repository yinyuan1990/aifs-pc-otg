「任意软件按 exe 限速」— 开发难度说明

对比不同技术路线：工作量、风险、合规与运维成本（供排期与决策参考）

结论摘要

在 Windows 上对其他进程做全流量上/下行限速，本质是系统网络路径上的整形。 难度从低到高大致为：集成商业产品 API < WinDivert 用户态方案 < 自研 WFP/NDIS 内核驱动。 「无 UI、仅命令/服务 + 后台下发」不改变内核路线的难度，只减少界面开发量。

一、为什么难？

  • 限速对象不是「你自己的 recv/send」，而是任意进程经内核发出的报文，必须在数据路径上排队、延迟或丢弃。
  • 需要把报文五元组可靠关联到进程（PID / 映像名），并处理连接创建/关闭、IPv4/IPv6、多网卡、VPN 等边角。
  • 任何内核或驱动级错误都可能导致蓝屏；第三方安全软件、反作弊可能冲突或拦截。
  • 第三方驱动分发需代码签名（EV + 微软门户等），有费用与审核周期，和「写代码」并行存在。

二、路线对比表

路线 开发难度 粗估周期（熟手） 要点
调用 NetLimiter 等已安装产品的官方 API / REST 低～中 约 0.5～2 周（协议 + 服务壳） 依赖终端授权与安装；商务/EULA 与是否可再分发需单独确认。
WinDivert（本仓库 winshaper 方向） 中高 MVP：约 2～6 周；IPv6/UDP/热更新/极致稳定：+数周～数月 无自研内核 callout，但要在用户态做好 PID 映射、令牌桶、队列与测试；驱动由 WinDivert 提供（LGPL）。
自研 WFP Callout 或 NDIS LWF 很高 MVP：常按2～4 人月量级估；产品级 + 签名 + 兼容：更长 完全自控与分发形态最优，但调试、稳定性、签名与长期维护成本最高。
仅在自有子进程内限速（如单一 worker 的下载/WebSocket） 低 数天量级 不解决「任意 exe」需求，只是策略门闕 + 自用 socket 节流。

三、难度维度拆解（自研/WinDivert 类）

协议与产品层 后台 JSON、启停、规则持久化：相对可控。
用户态整形逻辑 令牌桶、每进程聚合、队列上限、与 WinDivert 重注入的配合。
关联 PID SOCKET/FLOW 事件与首包竞态、UDP、IPv6 映射。
测试与兼容 多网卡、休眠恢复、代理、高 PPS、游戏/杀软环境。

四、本仓库 winshaper 当前实现

  • 已完成：IPv4 TCP、规则文件、SOCKET 层建表 + NETWORK 层整形雏形。
  • 未做或简化：IPv6 限速、UDP、热更新规则、与后台通道直连（需你方再接一层协议）。
  • 合规：使用 WinDivert 须遵守其 LGPL 及附带二进制/许可声明要求。

五、给排期用的「一句话」

若目标是任意 exe 全机限速 + 后台触发 + 无 UI：
用 WinDivert 比自研驱动省一个数量级，但仍要按中高级网络工程排期并预留大量测试；若必须零第三方闭源依赖且可随意打包驱动，则按内核团队 + 数月规划更稳妥。

文档随项目维护；数值为经验量级，以实际团队技能与目标平台为准。
