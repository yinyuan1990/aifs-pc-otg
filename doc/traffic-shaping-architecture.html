基于 WinDivert + Token Bucket 的进程级精准限速方案

1系统架构总览

整个限流系统由后端服务器、PC 客户端 (Phoenix)、子进程服务 (zjc_worker) 三个部分协同工作，实现从云端下发限速指令到本地内核级精准限流的完整链路。

3完整限流流程

Step 1 — 后端下发指令
管理员在 Web 页面发起限速
管理员在 Vue.js 后台选择目标设备，填写进程名 (如 CefSharp.BrowserSubprocess)、上传限速 (10KB/s)、下载限速 (10KB/s)、持续时间。 后端 BurstService 通过 STOMP 推送到 /topic/pc/{pcDeviceId}/shaper。
// 后端推送的 JSON 指令 { "action": "TRAFFIC_SHAPE", "processName": "CefSharp.BrowserSubprocess", "uploadBps": 10240, // 10 KB/s = 10240 bytes/sec "downloadBps": 10240, "durationSec": 30, "taskId": "task_20260412_001723_940" }
Step 2 — zjc_worker 接收并解析
子进程服务收到 STOMP 消息
zjc_worker (Windows Service) 通过 WinHTTP WebSocket 保持长连接， 订阅了 /topic/pc/{pcDeviceId}/shaper。 收到消息后解析 JSON，提取进程名和速率参数。
Step 3 — 写入规则文件
生成 zjc_shaper.rules 规则文件
将限速参数写入临时规则文件，格式为每行一条规则：
// zjc_shaper.rules 文件内容 CefSharp.BrowserSubprocess.exe 10240 10240 // 格式: 进程名 上传限速(B/s) 下载限速(B/s)
Step 4 — 启动 WinShaper 引擎
初始化三大核心组件
WinShaper 引擎在 zjc_worker 进程内以独立线程运行，按顺序初始化：
① FlowMap 线程
启动后台线程每 1 秒刷新网络连接→PID 映射表
② Rules 加载
从规则文件读取进程名和速率限制
③ Shape 主循环
打开 WinDivert NETWORK 层，开始拦截数据包
Step 5 — WinDivert 拦截数据包
内核驱动捕获所有 TCP/UDP 数据包
WinDivert 驱动在 Windows 网络栈 NETWORK 层注册过滤器 "tcp or udp"， 所有进出的 TCP 和 UDP 数据包都会被拦截到用户态，程序处理完后再决定放行或排队。
应用层 (CefSharp, Chrome, ...)send()/recv()
↕
Winsock / AFD 层Socket API
↕
🎯 WinDivert NETWORK 层 — 在此拦截!filter: tcp or udp
↕
NDIS 驱动层网卡驱动
↕
物理网络 (Ethernet / WiFi)硬件
Step 6 — 数据包归属识别
通过 FlowMap 查找数据包属于哪个进程
WinDivert NETWORK 层拦截到的数据包不带进程信息（只有 IP + 端口）， 需要通过 FlowMap 反查 PID。完整流程：
1. 解析数据包 → 提取 IP 头 (SrcAddr/DstAddr) + 端口号 (SrcPort/DstPort) + 协议 (TCP/UDP)
2. 构造查询 Key → 根据方向 (Outbound/Inbound) 确定 local/remote 地址和端口
3. 哈希查表 → TCP: 完整五元组匹配 (localIP:port ↔ remoteIP:port + proto)；UDP: 仅匹配本地端口
4. 获得 PID → 再通过 QueryFullProcessImageNameW(pid) 获取进程 .exe 名称
Step 7 — 规则匹配
进程名模糊匹配限速规则
拿到进程 .exe 名称后，与规则列表逐一比对（大小写不敏感 + .exe 后缀自动补全/去除）。 匹配成功则获得该规则的 up_bps 和 dn_bps 限速值。
// 模糊匹配示例 "CefSharp.BrowserSubprocess" → 匹配 "CefSharp.BrowserSubprocess.exe" ✅ "CefSharp.BrowserSubprocess.exe" → 匹配 "CefSharp.BrowserSubprocess" ✅ "chrome.EXE" → 匹配 "Chrome.exe" ✅ (不区分大小写)
Step 8 — Token Bucket 限速
令牌桶算法决定放行或排队
每个规则维护上传 + 下载两个独立的令牌桶。数据包到来时：
令牌足够 (tokens ≥ packet_size) → 扣减令牌，立即放行 (WinDivertSend)
令牌不足 (tokens < packet_size) → 排入等待队列，等下次 drain 循环令牌补充后再放行
Result — 限速生效
目标进程网速被精确控制
不匹配规则的数据包直接放行 (零延迟)，匹配的数据包被令牌桶精准控速。 效果等同于 NetLimiter 等商业软件，但完全自研、可远程控制。

4Token Bucket 令牌桶算法详解

令牌桶是流量整形的核心。它以恒定速率产生"令牌"（每个令牌代表 1 字节的发送配额），数据包必须消耗足够令牌才能放行。

算法参数
参数含义本系统取值
rate_bps令牌产生速率 (bytes/sec)由后端下发，如 10240 = 10KB/s
tokens当前可用令牌数 (bytes)实时计算，初始 = rate_bps
cap令牌桶容量上限rate_bps × 2 (允许小突发)
last_qpc上次补充时间戳QueryPerformanceCounter 高精度计时
bucket_refill — 令牌补充
void bucket_refill(Bucket *b, int64_t rate_bps) { double dt = (now - b->last_qpc) / frequency; b->tokens += dt * rate_bps; // 上限 = rate × 2 (防止空闲后突发过大) if (b->tokens > rate_bps * 2.0) b->tokens = rate_bps * 2.0; }

每次数据包到来时计算距上次的时间差 dt， 按 dt × rate 补充令牌。 使用 QueryPerformanceCounter 实现微秒级精度。

bucket_try — 令牌消费
BOOL bucket_try(Bucket *b, int64_t rate, UINT nbytes) { bucket_refill(b, rate); if (b->tokens >= nbytes) { b->tokens -= nbytes; // 扣减 return TRUE; // 放行 } return FALSE; // 排队 }

尝试消费 nbytes 个令牌。 足够则扣减并立即放行数据包； 不足则返回 FALSE，数据包进入排队等待。

为什么上限是 rate × 2？ 允许短暂的突发流量（如 TCP 慢启动），但不会偏离限速太多。 如果桶容量 = rate × 1，TCP 会频繁出现排队延迟导致性能下降。

5FlowMap 连接映射机制

WinDivert 在 NETWORK 层拦截数据包时不包含进程信息（只有 IP + 端口）， 需要一种机制将 网络五元组 (SrcIP, SrcPort, DstIP, DstPort, Protocol) 反向映射到 进程 PID。

为什么不用 WinDivert SOCKET 层？
跨 Session 限制：zjc_worker 作为 Windows Service 运行在 Session 0 (SYSTEM)， 而用户进程 (如 CefSharp) 运行在 Session 1+。WinDivert SOCKET 层只能捕获同 Session 的连接事件， 导致 99% 数据包查不到 PID (no_pid 极高)。
解决方案：使用 Windows IP Helper API (GetExtendedTcpTable / GetExtendedUdpTable) 定时扫描系统全局连接表，不受 Session 隔离限制。

FlowMap 架构

TCP 映射 — 完整五元组
struct FNode { UINT32 local[4]; // 本地 IP (IPv4映射到IPv6格式) UINT32 remote[4]; // 远端 IP UINT16 local_port; UINT16 remote_port; DWORD pid; // 所属进程 PID }; // 哈希表: 8192 个桶，链表法解决冲突

TCP 有明确的连接状态，系统表包含完整的本地/远端地址+端口，可精确匹配。 只录入 ESTABLISHED 状态的连接。

UDP 映射 — 仅本地端口
struct UNode { UINT16 local_port; // 本地端口 DWORD pid; // 所属进程 PID }; // 哈希表: 4096 个桶 // UDP 系统表没有远端地址信息，只能按本地端口匹配

UDP 无连接状态，系统表只有本地绑定端口，因此用本地端口作为唯一 key。 同端口的所有 UDP 流量归属同一进程。

刷新机制

flowmap_socket_thread — 每秒全量刷新
DWORD WINAPI flowmap_socket_thread(LPVOID arg) { while (!g_stop) { refresh_from_system_tables(); // 清空旧表 + 重建 Sleep(1000); // 每 1 秒刷新一次 } } void refresh_from_system_tables() { map_clear_all(); // 清空哈希表 GetExtendedTcpTable(AF_INET); // IPv4 TCP GetExtendedUdpTable(AF_INET); // IPv4 UDP GetExtendedTcpTable(AF_INET6); // IPv6 TCP GetExtendedUdpTable(AF_INET6); // IPv6 UDP }

6Shape 主循环 — 每个数据包的处理流程

这是整个限流系统的核心循环，每一个进出网卡的 TCP/UDP 数据包都会经过这段逻辑：

while (!g_stop) { // ① 从内核获取一个数据包 (阻塞等待) WinDivertRecv(g_net, pkt, &plen, &addr); // ② 解析 IP 头 + TCP/UDP 头，提取端口号 WinDivertHelperParsePacket(pkt, plen, &ip, &ip6, &tcp, &udp); // ③ 通过 FlowMap 查找此数据包属于哪个 PID pid = flowmap_lookup_ipv4(outbound, ip, src_port, dst_port, proto); if (!pid) { pkt_forward(); continue; } // 找不到 PID → 直接放行 // ④ PID → 进程名 → 匹配限速规则 ri = rules_match_pid(pid); if (ri < 0) { pkt_forward(); continue; } // 不在规则中 → 直接放行 // ⑤ Token Bucket 判断 if (bucket_try(bucket, rate, plen)) { pkt_forward(); // 令牌足够 → 立即放行 } else { pkt_enqueue(); // 令牌不足 → 排队等待 } // ⑥ 尝试释放所有规则的排队数据包 (令牌可能已补充) drain_all(h, 64); }

运行时统计 (每 5 秒输出到 zjc_shaper.log)

total
拦截的总数据包数
no_pid
FlowMap 中找不到 PID
no_rule
PID 不匹配任何规则
shaped
被限速处理的数据包
passed
匹配规则但限速=0 (无限)
诊断技巧：如果 no_pid 占比过高 (>50%)，说明 FlowMap 映射有问题； 如果 shaped = 0，说明进程名匹配失败或目标进程无流量。

7数据包排队与释放机制

当令牌不足时，数据包不会被丢弃，而是进入内存队列等待令牌补充后再发送，保证不丢包。

排队结构 — 每个规则独立
typedef struct { Bucket up, dn; // 上传 + 下载各一个令牌桶 PktQ *uq_head/tail; // 上传方向排队链表 PktQ *dq_head/tail; // 下载方向排队链表 size_t uq_bytes; // 上传队列总字节数 size_t dq_bytes; // 下载队列总字节数 } RuleState; // 单方向队列上限 = 4 MB，防止内存溢出 // 超过上限的包直接放行 (降级为不限速，但不丢包)
drain_all — 释放排队数据包

每次处理完一个新数据包后，都会尝试把所有规则的排队包释放出去（令牌可能在这段时间内补充了）：

for (每个规则 i) { while (队列不空 && budget > 0) { if (上传队头 && bucket_try(up, 包大小)) → WinDivertSend() → 出队; if (下载队头 && bucket_try(dn, 包大小)) → WinDivertSend() → 出队; } }
